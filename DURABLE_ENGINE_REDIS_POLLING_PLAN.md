# Durable engine Redis polling and wake-up plan

Status: Phase 1 implemented; real-Redis performance acceptance pending. Later notification phases remain proposed.

This document extends the completed [durable engine implementation plan](DURABLE_ENGINE_PLAN.md). It addresses
the Redis traffic generated by idle durable deployments without reopening the engine's lifecycle, persistence, or
public execution contracts.

## Decision summary

Deliver the work in two independent stages:

1. Reduce fixed polling cost without changing coordination semantics:
   - inspect each sorted set before requesting Redis time;
   - use separate worker and lease-maintenance intervals;
   - retain the existing polling behavior as the compatibility baseline.
2. Add an optional event-driven wake-up path:
   - keep the `runnable` and `lease-expiry` sorted sets as the only durable scheduling truth;
   - use Redis Pub/Sub only as an advisory wake-up signal;
   - sleep until a notification, the next authoritative deadline, or a bounded safety timeout;
   - fall back to polling automatically whenever notifications are unavailable.

Do not replace the sorted sets with a blocking queue or Redis Stream. Those approaches introduce a second durable
work-delivery state machine and conflict with the existing reducer-owned leases, retries, and fencing.

## Problem statement

Before Phase 1, an idle durable deployment performed Redis work every 250 milliseconds:

- each configured worker slot calls `claim()`;
- one maintenance task calls `maintain()`;
- `claim()` issues `TIME` and `ZRANGEBYSCORE` against `runnable`;
- `maintain()` issues `TIME` and `ZRANGEBYSCORE` against `lease-expiry`.

The default idle command rate is therefore:

```text
commands/second = deployments * (worker_concurrency + 1) * (1 / poll_interval) * 2
```

The supplied Redis trace contained two deployment namespaces, one worker per deployment, and the default 0.25-second
interval:

```text
2 deployments * (1 worker + 1 maintenance task) * 4 polls/second * 2 commands
= approximately 32 Redis commands/second while idle
```

The namespaces map to:

- `8747bf...` -> `durable_chat_with_website`;
- `5a53f9...` -> `chat_with_website`.

This is expected fixed polling rather than leaked work, but the default cadence is unnecessarily aggressive and
scales linearly with deployments, worker concurrency, and Hayhooks processes.

## Goals

- Reduce empty-idle Redis commands from approximately 32 to no more than 4 commands/second for the observed
  two-deployment configuration in Phase 1 (approximately 87.5%), with any further reduction treated as a separate
  notification-stage benefit.
- Preserve prompt work pickup for interactive examples.
- Preserve bounded recovery after worker or process failure.
- Preserve Redis as the authoritative clock for due-time and lease decisions.
- Preserve the Python reducer as the only lifecycle authority.
- Preserve cross-process execution and Redis restart recovery.
- Preserve Redis 6.2 as the minimum supported Redis version.
- Preserve cluster-safe per-deployment key layout.
- Keep Redis notifications advisory so their loss cannot lose or strand work.
- Keep polling available as a documented operational fallback.

## Non-goals

- Eliminating all Redis traffic while a durable deployment is running.
- Providing exactly-once application effects.
- Replacing Redis with a dedicated message broker.
- Replacing the durable engine with Celery, RQ, ARQ, or another job framework.
- Reworking the SSE stream polling contract.
- Changing lifecycle states, reducer commands, fences, attempt counters, or retry semantics.
- Adding Redis keyspace-notification configuration requirements.
- Requiring Redis 7 features such as sharded Pub/Sub or Redis Functions.

## Required invariants

The following constraints from `DURABLE_ENGINE_PLAN.md` remain non-negotiable.

### Lifecycle authority

`engine.decide()` remains the only code that decides lifecycle state. Wake-up code may cause a worker to retry a
claim, but it may not assign status, fence, attempt, lease, retry, cancellation, or terminal fields.

### Durable scheduling truth

The `runnable` and `lease-expiry` sorted sets remain derived durable indexes maintained atomically with control state.
A notification is only a hint that an index may have changed.

### Authoritative time

Redis `TIME` remains authoritative whenever the store decides whether work or a lease is due. The runtime may use an
authoritative delay returned by the store with `asyncio`'s monotonic timer, but it must not compare Redis timestamps
with the host wall clock.

An empty sorted set requires no time comparison. Skipping `TIME` after proving the index is empty does not weaken this
invariant.

### Fencing and recovery

Every claim and owned transition continues through the existing fenced reducer path. A lost notification may add
latency only; it must not affect correctness or require manual repair.

### Store portability

The memory and Redis stores continue to implement the same runtime-facing behavior. Redis-specific notification
plumbing stays in the Redis implementation and server integration.

## Alternatives considered

### A. Increase the existing interval only

Set `HAYHOOKS_DURABLE_POLL_INTERVAL_SECONDS=1` or change its default.

Advantages:

- no persistence or protocol changes;
- reduces the observed load from approximately 32 to 8 commands/second;
- already available to operators.

Disadvantages:

- couples job pickup and lease recovery;
- still scales linearly with every deployment and process;
- cannot provide both low latency and low idle traffic.

Decision: retain as an immediate operator workaround, but do not treat it as the complete design.

### B. Query the index before requesting Redis time

Use the lowest sorted-set member to establish whether an index is empty:

```text
ZRANGE index 0 0 WITHSCORES
├── empty: return without TIME
└── non-empty: call TIME and compare the authoritative score
```

For maintenance, read at most `MAINTENANCE_BATCH_SIZE` members in score order. After obtaining Redis time, process the
due prefix and stop at the first future deadline.

Advantages:

- halves command count when indexes are empty;
- removes one network round trip from empty scans;
- does not change pickup or recovery latency;
- preserves Redis time for every actual due-time decision.

Disadvantages:

- non-empty future indexes still require two commands;
- fixed polling remains.

Decision: implement in the first delivery stage.

### C. Separate worker and maintenance cadences

Introduce an independent maintenance interval. Implemented Phase 1 defaults:

```text
worker poll interval:       1.0 second
maintenance poll interval: 1.0 second
lease duration:             30 seconds, unchanged
```

With option B and the observed two deployments, the empty-idle estimate becomes:

```text
worker scans:      2 deployments * 1 scan/second = 2.0 commands/second
maintenance scans: 2 deployments * 1 scan/second = 2.0 commands/second
total:                                                   4.0 commands/second
```

This is approximately an 87.5% reduction from the observed 32 commands/second. The one-second maintenance default
captures most of the available fixed-polling reduction while adding at most one second after lease expiry. Longer
maintenance intervals remain available for recovery-tolerant deployments.

Advantages:

- reflects the different latency requirements;
- simple operational controls;
- preserves fixed, bounded behavior;
- independent of notification support.

Disadvantages:

- still polls indefinitely;
- adds one public setting;
- customized short leases may require a customized maintenance interval.

Decision: implement in the first delivery stage.

### D. Adaptive polling with jitter

Increase the interval after consecutive empty scans and reset it after work is found. Add jitter so deployments do not
poll in synchronized bursts.

Advantages:

- much lower steady-state traffic after long idle periods;
- no Redis feature beyond the existing store.

Disadvantages:

- cross-process submissions can wait until the maximum backoff;
- scheduled retries and expired leases become less predictable;
- latency depends on prior idleness;
- jitter spreads traffic but does not reduce its total volume.

Decision: do not use adaptive polling as the primary mechanism. Consider bounded jitter later only to prevent bursts.

### E. Advisory Redis Pub/Sub wake-ups

Publish a small deployment-change notification after a committed transition makes work runnable or creates a new
lease. Workers subscribe before scanning and wait for a notification, an authoritative deadline, or a safety timeout.

Advantages:

- near-zero idle sorted-set polling;
- low normal pickup latency;
- no duplicate durable queue state;
- works with Redis 6.2;
- notification loss is harmless when bounded safety polling remains.

Disadvantages:

- Pub/Sub delivery is at-most-once;
- needs reconnect and scan-before-wait race handling;
- regular Pub/Sub has cluster-wide propagation rather than Redis 7 sharded Pub/Sub behavior;
- adds Redis ACL requirements for `PUBLISH` and `SUBSCRIBE`;
- adds a long-lived subscriber connection.

Decision: recommended second delivery stage, initially opt-in.

### F. Redis keyspace notifications

Subscribe to Redis-generated events for sorted-set changes.

Advantages:

- avoids explicit `PUBLISH` calls in store transitions.

Disadvantages:

- disabled by default;
- requires server configuration often unavailable in managed Redis;
- uses Pub/Sub delivery and therefore still loses events during disconnects;
- may expose unrelated key activity depending on configuration;
- still requires safety polling.

Decision: reject.

### G. Blocking lists or blocking sorted-set pops

Use `BLPOP`, `BZPOPMIN`, or `BZMPOP` to park worker connections.

Advantages:

- Redis blocks the connection without repeated commands;
- list pushes can wake one waiting worker.

Disadvantages:

- `BZPOPMIN` pops the lowest score even when a scheduled item is not due;
- popping removes the runnable index member before the fenced reducer claim commits;
- a list becomes a second queue index that must be reconciled with control state;
- scheduled retries still require a separate deadline scheduler;
- blocking calls require dedicated Redis connections;
- multi-deployment blocking becomes awkward under Redis Cluster hash slots.

Decision: reject for the existing sorted-set architecture.

### H. Redis Streams as the primary worker queue

Use `XREADGROUP BLOCK` and consumer-group pending entries for work delivery and recovery.

Advantages:

- durable blocking delivery;
- established consumer distribution and acknowledgement primitives;
- low idle command volume.

Disadvantages:

- consumer pending-entry ownership duplicates the engine's lease and fence model;
- delayed retries still need a sorted-set scheduler;
- stream acknowledgements add another lifecycle transition boundary;
- existing control records and the stream can disagree after partial failures unless all mutations are redesigned;
- memory-store parity becomes substantially more complex;
- this changes the engine from a state machine with derived indexes into a queue-centric design.

Decision: reject unless the durable engine is intentionally redesigned around a Redis-only queue in a future major
version.

### I. Lua scripts or Redis Functions

Combine `TIME`, index lookup, and possibly claim logic on the Redis server.

Advantages:

- fewer client/server round trips;
- one visible script command can replace multiple client commands;
- atomic server execution.

Disadvantages:

- polling frequency and most Redis work remain;
- moving claim decisions into Lua duplicates the Python reducer;
- Redis Functions require Redis 7, while the engine supports Redis 6.2;
- scripts require loading, cache-miss, failover, and version-management behavior.

Decision: do not use scripting to solve idle polling. Reconsider only after profiling shows transaction round trips,
rather than idle frequency, are the bottleneck.

### J. One elected maintenance leader

Elect one process per deployment to scan lease expiry.

Advantages:

- removes duplicate maintenance scans across replicas.

Disadvantages:

- does not improve the observed single-process case;
- leader election and renewal create their own Redis traffic;
- failure detection and handover become new correctness-sensitive paths.

Decision: defer. Reconsider only when multi-replica maintenance traffic is measured as significant after the earlier
stages.

## Recommended target design

### Durable truth and advisory signals

The target flow is:

```text
submit / resume / retry / recovery
               │
               ├── commit control, payload, and sorted-set index
               └── best-effort publish: runnable index changed
                                      │
worker: claim ──┬── claimed ──────────┴── execute through existing fenced path
               └── none ── wait for notification, next due delay, or safety timeout

claim / lease creation
               │
               ├── commit running control and lease index
               └── best-effort publish: lease index may have an earlier deadline
                                      │
maintenance: scan due leases ─────────┴── wait for notification, next expiry, or safety timeout
```

The notification must never carry input, checkpoint, result, owner, idempotency material, error, or stream data. A
deployment digest and event kind are sufficient.

### Store-computed wait hints

The runtime must not compare Redis timestamps to its own wall clock. The store should therefore return relative wait
hints computed from its authoritative clock.

Proposed internal result shape:

```python
@dataclass(frozen=True, slots=True)
class ClaimResult:
    plan: TransitionPlan | None
    retry_after_seconds: float | None
```

Rules:

- a claimed execution returns its plan and no wait hint;
- an empty runnable index returns no plan and `None`;
- a future runnable member returns no plan and a non-negative relative delay;
- a due candidate lost to contention returns a zero delay so the worker scans again;
- delay calculation uses the store clock;
- the runtime uses the delay only as a monotonic sleep duration.

`maintain()` should similarly return the relative delay to the next known lease expiry:

- return `0` when a full maintenance batch was processed, because more due entries may remain;
- return a positive delay when the earliest lease is in the future;
- return `None` when the lease index is empty.

These are internal store/runtime contracts, not public REST models.

### Notification feed semantics

The feed is advisory and coalescing:

- duplicate notifications are allowed;
- several changes may become one local wake-up;
- one notification may wake several local worker slots;
- workers always claim from durable state after waking;
- an empty wake-up is harmless;
- notification failure must not fail a transition that has already committed;
- reconnect always triggers an immediate durable scan.

The subscriber must be active before workers perform their first empty scan. A local latched event prevents a change
that arrives between the scan and `wait()` from being lost. Clearing an event after a wake is safe because every
woken worker scans durable state before waiting again.

### Redis notification topology

Prefer one notification hub per Redis client/URL and Hayhooks process, rather than one Pub/Sub connection per durable
deployment or worker.

The hub should:

- subscribe to one private channel derived from the durable key prefix;
- receive only deployment digest and event kind;
- route notifications to registered local deployment events;
- support dynamic deployment registration and removal;
- reconnect with bounded backoff;
- mark itself disconnected in health state;
- trigger all registered deployments to scan after reconnect;
- close before the shared Redis client closes.

Regular Pub/Sub is required for Redis 6.2 compatibility. Redis 7 sharded Pub/Sub may be evaluated later as an optional
cluster optimization, but cannot be required by this plan.

### Publishing rules

Publish `runnable` after a successful transaction that:

- creates a new queued execution;
- resumes a waiting execution;
- schedules an application retry, including a future retry;
- releases a failed post-claim read back to queued;
- recovers an expired lease back to queued.

Publish `lease` after a successful claim creates a new lease. Do not publish on every heartbeat:

- a heartbeat moves an existing deadline later and cannot create an earlier recovery deadline;
- a stale early maintenance wake is harmless;
- avoiding heartbeat publications prevents active-run notification noise.

Publishing occurs only after the durable Redis transaction succeeds. If the process fails between commit and publish,
the safety scan recovers the work. A publish error is recorded as notification health degradation, not returned as a
failed lifecycle operation after commit.

### Waiting rules

When notification mode is active, a worker waits for the minimum of:

- its store-provided next-runnable delay, if present;
- the notification safety interval;
- shutdown or deployment generation change.

When notification mode is inactive or disconnected, use the configured fixed worker interval.

Maintenance follows the same rule with its next-expiry delay and maintenance fallback interval.

Suggested initial notification safety interval: 30 seconds. This is not normal pickup latency; it bounds recovery from
a missed notification or subscriber outage.

## Delivery phases

### Phase 0 — Freeze the baseline

Tasks:

- add a reproducible Redis `MONITOR` measurement procedure for an isolated Redis instance;
- record idle commands for one and two deployments with worker concurrency one;
- record pickup latency for a newly submitted run;
- record lease recovery latency after killing a worker process;
- distinguish worker, maintenance, health, and SSE commands in the measurement notes;
- retain the supplied two-deployment trace as design evidence, not as a test fixture.

Acceptance:

- the baseline reproduces approximately 16 idle commands/second per deployment with the pre-Phase-1 defaults;
- measurements state Redis version, deployment count, worker concurrency, polling interval, and observation duration.

### Phase 1 — Reduce fixed polling cost

Tasks:

- change Redis claim lookup to inspect the lowest runnable member before calling `TIME`;
- change Redis maintenance lookup to inspect the earliest bounded lease batch before calling `TIME`;
- reject invalid runnable members or scores as store corruption, and remove invalid lease-index entries as repairable
  derived-index corruption;
- add `maintenance_interval_seconds` to `RuntimeConfig`;
- add `durable_maintenance_interval_seconds` to server settings;
- add `HAYHOOKS_DURABLE_MAINTENANCE_INTERVAL_SECONDS` to environment documentation;
- change the default worker polling interval from `0.25` to `1.0` seconds;
- use a default maintenance interval of `1.0` second;
- supervise unexpected worker-task exits immediately rather than from the Redis maintenance loop;
- preserve `HAYHOOKS_DURABLE_POLL_INTERVAL_SECONDS` for compatibility;
- update documentation so worker and recovery latency are described separately;
- update tests with explicit short intervals where they depend on rapid recovery.

Tests:

- empty runnable lookup performs no `TIME` command;
- empty lease lookup performs no `TIME` command;
- a future runnable score uses Redis time and is not claimed early;
- a due runnable score still claims through the reducer;
- future leases are not recovered early;
- expired leases still recover in bounded batches;
- invalid runnable members and scores report corruption, while invalid lease entries are removed without requesting
  Redis time;
- worker and maintenance loops use their independent intervals;
- configuration rejects non-finite, zero, or negative intervals;
- environment settings construct the expected runtime configuration.

Acceptance:

- the two-deployment empty-idle rate is no more than 4 relevant Redis commands/second on average;
- ordinary pickup delay is bounded by the configured worker interval;
- expired-lease recovery delay is bounded by the configured maintenance interval after lease expiry;
- all existing store contract, runtime, Redis integration, process-recovery, FastAPI, and example tests pass;
- no Redis data migration is required.

### Phase 2 — Add authoritative deadline hints

Tasks:

- introduce the internal claim result carrying an optional relative wait hint;
- make memory and Redis stores compute equivalent wait hints from their own clocks;
- make maintenance return an optional next-expiry delay;
- return zero after contention or a full due batch;
- update the runtime to cap every hint with its fixed fallback interval;
- keep behavior equivalent when no notification feed exists.

Tests:

- empty, future, due, contended, corrupt, and full-batch outcomes return correct hints;
- host wall-clock changes do not affect runtime waiting decisions;
- a newly queued earlier item is still discovered within the fallback interval;
- zero-delay outcomes do not busy-loop after the underlying contention clears;
- shutdown interrupts deadline waits promptly.

Acceptance:

- scheduled retries are claimed no earlier than their Redis deadline;
- scheduled retries are normally claimed within one event-loop turn after their deadline when no earlier notification
  arrives;
- the runtime never compares a Redis millisecond timestamp to host wall time.

### Phase 3 — Add advisory Pub/Sub wake-ups

Tasks:

- add an internal Redis notification hub owned by the server lifespan;
- create the hub from the same Redis configuration as durable stores;
- register and unregister deployments during durable install/remove;
- subscribe before starting deployment workers;
- add best-effort runnable and lease publications after successful store commits;
- route notifications by deployment digest without exposing execution data;
- add a race-safe local latch per deployment and event kind;
- wake deployments after subscriber reconnect;
- add bounded notification reconnect backoff;
- keep fixed polling active whenever notification mode is disabled or disconnected;
- add a notification safety interval;
- close the notification hub before closing the shared Redis client;
- initially expose notification mode as opt-in configuration.

Proposed settings:

| Variable | Initial default | Purpose |
|---|---:|---|
| `HAYHOOKS_DURABLE_WAKEUP_MODE` | `poll` | `poll` or `pubsub` during rollout |
| `HAYHOOKS_DURABLE_NOTIFICATION_SAFETY_INTERVAL_SECONDS` | `30` | Maximum delay after a missed notification |
| `HAYHOOKS_DURABLE_POLL_INTERVAL_SECONDS` | `1` | Worker fallback when notification mode is unavailable |
| `HAYHOOKS_DURABLE_MAINTENANCE_INTERVAL_SECONDS` | `1` | Maintenance fallback when notification mode is unavailable |

Tests:

- submission wakes an already-idle worker;
- resume wakes an already-idle worker;
- a scheduled future retry wakes workers to recompute the deadline but is not claimed early;
- lease creation wakes maintenance to register an earlier deadline;
- heartbeats do not publish notifications;
- duplicate and coalesced notifications are harmless;
- a notification between empty scan and wait is observed;
- publish failure after commit does not fail the committed operation;
- a lost notification is recovered by the safety timeout;
- subscriber disconnect changes health and falls back to polling;
- subscriber reconnect triggers an immediate scan;
- multiple worker slots do not cross-deliver executions;
- multiple processes compete through existing fenced claims;
- dynamic undeploy removes subscriptions and leaves no task behind;
- Redis restart recovers subscriptions and durable work;
- shutdown does not wait for the safety timeout;
- notification payloads contain no execution or user data.

Acceptance:

- with Pub/Sub healthy and no indexed work, sorted-set and `TIME` commands average no more than one safety scan per
  configured safety interval and deployment;
- normal local-Redis submission-to-claim latency is measured and documented;
- a disconnected subscriber cannot strand work beyond the configured fallback bound;
- one Hayhooks process uses no more than one Pub/Sub subscriber connection per Redis client/URL;
- Redis 6.2 integration and process-restart tests pass;
- poll mode remains fully functional and requires no Pub/Sub ACL permissions.

### Phase 4 — Roll out and decide the default

Tasks:

- ship Phase 1 independently;
- ship Pub/Sub mode as opt-in;
- test standalone Redis, Redis Sentinel/failover where available, and Redis Cluster behavior;
- document required Redis ACL commands;
- measure command volume, connection count, notification failures, pickup latency, and recovery latency;
- change the default wake-up mode only after the safety fallback has been exercised in CI and a process-restart test;
- retain explicit poll mode as a permanent compatibility and incident-response option.

Acceptance:

- rollback from Pub/Sub to polling requires configuration only;
- no stored execution or index migration is required in either direction;
- operations documentation includes expected idle traffic for both modes;
- the final default is recorded in this document and the environment-variable reference.

## Race and failure analysis

| Scenario | Required behavior |
|---|---|
| Submission commits before publish | Safety polling finds the runnable item |
| Publish succeeds before worker begins waiting | Latched local event causes an immediate rescan |
| Pub/Sub message is duplicated | Extra empty claim is harmless |
| Several changes coalesce into one wake | Worker claims repeatedly while due work exists |
| Subscriber disconnects | Health degrades and fixed polling resumes |
| Subscriber reconnects | Resubscribe, latch all deployments, scan immediately |
| New earlier retry is scheduled during a deadline wait | Notification interrupts the wait and recomputes the earliest deadline |
| Notification for a future retry is lost | Safety polling discovers it; authoritative deadline prevents early claim |
| Worker crashes after claim | Lease index remains authoritative; maintenance recovers after expiry |
| Heartbeat extends a lease | An early maintenance wake may occur; no late recovery is introduced |
| Deployment is replaced or removed | Generation checks stop old waits; hub registration is removed |
| Redis restarts | Store backoff, subscriber reconnect, and safety scan restore progress |
| Pub/Sub ACL is denied | Deployment remains operational in poll mode and reports notification degradation |
| Multiple workers wake together | Fenced transactional claim allows only one winner per execution |

## Observability

Do not log each poll or notification. Add only bounded operational state:

- configured worker and maintenance intervals;
- configured and effective wake-up mode;
- notification connection state;
- notification error streak or last error type;
- whether fixed fallback polling is active;
- existing worker, maintenance, and store health.

Useful debug logs:

- notification subscriber connected;
- notification subscriber disconnected, with exception type;
- notification subscriber recovered;
- wake-up mode fell back to polling;
- wake-up mode returned to Pub/Sub.

Never log notification payload contents beyond deployment digest and event kind. Never log execution payloads, owner
identifiers, run IDs, idempotency material, checkpoints, results, errors, or stream chunks from this path.

## Redis and security considerations

- Poll mode continues to require the existing Redis command permissions only.
- Pub/Sub mode requires `PUBLISH`, `SUBSCRIBE`, and connection permissions for the private channel.
- Notification channel names use the configured durable prefix and contain no user-controlled execution data.
- Regular Pub/Sub is used for Redis 6.2 compatibility.
- Redis 7 sharded Pub/Sub is a future optimization, not an automatic behavior change.
- Do not require `CONFIG SET` or keyspace notifications.
- Do not publish application data.
- Best-effort notification failures must not turn a successfully committed transition into an apparent failed write.

## Performance verification

Measure each scenario for at least 60 seconds after startup settles:

| Scenario | Deployments | Workers/deployment | Expected result |
|---|---:|---:|---|
| Pre-Phase-1 baseline | 2 | 1 | Approximately 32 idle commands/second |
| Phase 1, empty indexes | 2 | 1 | No more than 4 relevant commands/second |
| Pub/Sub healthy | 2 | 1 | No repeated index commands between safety scans |
| Pub/Sub disconnected | 2 | 1 | Bounded fallback at configured fixed intervals |
| Worker concurrency scaling | 2 | 4 | Phase 1 scales with workers; Pub/Sub remains notification-driven |
| Ten idle deployments | 10 | 1 | Connection and command counts remain within documented bounds |

Record separately:

- `TIME` count;
- runnable index lookup count;
- lease index lookup count;
- `PUBLISH` count;
- subscriber connection count;
- mean and p95 submission-to-claim latency;
- mean and p95 post-expiry lease-recovery latency;
- reconnect-to-first-scan latency.

Do not use total Redis command count alone because health reads, execution streaming, active heartbeats, and test setup
commands are legitimate but unrelated to idle scheduling.

## Compatibility and migration

- No Redis key or value migration is required for Phase 1.
- Pub/Sub adds no durable keys.
- Existing `HAYHOOKS_DURABLE_POLL_INTERVAL_SECONDS` remains supported.
- Direct `RuntimeConfig` callers receive documented new defaults and may retain old behavior by setting both intervals
  to `0.25`.
- Poll mode remains available permanently.
- Redis 6.2 remains supported.
- Memory store behavior remains deterministic and does not require Redis-style notifications.
- Existing terminal retention, idempotency, capacity, progress, and stream limits do not change.
